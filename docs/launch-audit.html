Stack. Monorepo: NestJS 11 API · Next.js 16 storefront (web) · Vite/React admin console · Expo/React Native mobile app. Product under audit is the web storefront plus its API — that is what is deployed and what customers will use.

The finding that decides the launch date

Phone OTP is the only customer sign-in method — email sign-in is behind ENABLE_EMAIL_LOGIN, which is off. In production, with no WhatsApp credentials configured, the message channel throws by design:

apps/api/src/notifications/log.channel.ts if (process.env.NODE_ENV === 'production') { this.logger.error('Phone sign-in is on but no message channel is configured…'); throw new ServiceUnavailableException('Unable to send a verification code right now'); }

No customer can sign in on production today. Buying still works — a guest pays through Cashfree and we build the account from the phone they verified — but a returning customer cannot get back into it. This is A1 in your own task list and it is blocked on a WhatsApp Business number.

02

Login flow

PassP2
Evidence
Phone + 6-digit OTP. Rate limits proven live, not just written: 5 per phone per 15 min, 10 per IP per hour, plus a daily ceiling. Covered by otp-rate-limit.spec.ts and 141 passing API tests. Wrong code returns a clear refusal; the modal cannot be dismissed by clicking outside.
Problem
Only that it cannot deliver a code in production — see the blocker above. The flow itself is sound.
Fix
Nothing in the flow. Ship the message channel.
03

Password reset

PassP2
Correction
This audit originally said no password reset existed anywhere. That was wrong. I searched for forgot-password and resetToken — the names a self-service flow would use — and concluded from their absence that nothing existed. What exists is an admin-driven reset, which those searches could not find.
Evidence
PATCH /users/staff/:id/password, guarded by @Roles(SUPER_ADMIN), with a console screen behind it. It refuses non-staff accounts, hashes with bcrypt, and writes an audit entry with the password redacted. Now covered by four tests that assert the manager can actually sign in afterwards, the old password stops working, a non-super-admin gets 403, and a customer account is refused with nothing written to it.
Problem
One real edge remains, much smaller than the one reported: a super admin who forgets their own password has nobody above them to reset it, so that case still ends in a database write.
Fix
Keep two super admins, so one can always reset the other. Cheaper and less to go wrong than an emailed reset flow for a handful of staff.

PassP2

09

Network failure states

PassP1
Evidence
The fallback catalogue is gone. It was a hardcoded list carrying a hardcoded ₹1450 and a slug that 404s, served silently whenever a catalogue call failed — so an outage produced a shop that looked open, quoted a price nobody maintained, and sent every card to a dead page. The product page was worse: its lookup ended in FALLBACK_PRODUCTS[0], so a failed fetch showed the ghee under whichever URL the customer had opened.

with the API genuinely stopped: /products cannot-load: true retry: true price shown: false /products/…-vedic-ghee cannot-load: true retry: true price shown: false

Problem
None outstanding. Shop and product page say they cannot load and offer a retry and a WhatsApp number; the homepage shelf removes itself rather than showing an empty band.
Fix
Done. Worth knowing for future tests: blocking the browser's requests proves nothing here now that these pages render on the server. The first attempt at verifying this passed while the fix did nothing, because Next had already fetched and seeded the page.
10

Session expiry

PassP2
Evidence
Every authenticated call goes through one wrapper; a 401 clears the stored session and raises a sessionExpired flag rather than leaving a half-authenticated screen. session.spec.ts A8 asserts a rejected token empties the account page — this exact bug shipped once, rendering a name and orders from localStorage while every write failed. The admin console clears its token on 401 too.
Problem
Expiry mid-payment is not proven. The claim token carries a guest through confirm, so the design should hold, but it was not exercised.
Fix
Beta task 4 covers it.
11

Unsaved changes

PassP1
Evidence
The product editor warns before losing work. Dirtiness is a serialised snapshot compared against the state as loaded, rather than a flag every setter has to remember — a boolean maintained in twenty places gets forgotten in the twenty-first, and that failure is silent. Tab switches and save-in-flight are excluded, because a warning that cries wolf teaches people to dismiss it unread. Covered by unsaved-changes.spec.ts, confirmed to discriminate by disabling the guard and watching it fail.
Problem
Only the product editor is covered. The hook is generic and unused elsewhere.
Fix
Apply it to the other long editors if they start losing work. The storefront's forms are short enough not to need it.
12

Duplicate submissions

PassP1
Evidence
The money path is defended at three levels: a single-use claim token; a basket fingerprint in the gateway order id so an unchanged basket reuses the same order rather than creating a second; and a replay-safe webhook — shiprocket-webhook.spec.ts proved a repeat delivery does not take stock twice or burn a second invoice number, and the same guard covers Cashfree. Buttons disable while pending in six components.
Problem
Double-tap on Add to cart was not explicitly tested, and neither was a rapid double submit of the review form.
Fix
Beta task 5. The payment path — the one that costs money — is covered.
13

Back navigation

Cannot verifyP1
Evidence
Cashfree opens in a modal on the same page rather than a separate route, which is the right call — there is no page to go back from. Their SDK reports error.code === 'payment_aborted' when a customer answers “Yes, Leave” to their own prompt, and the flow treats that as a cancel rather than a failure.
Problem
The browser back button and the Android back gesture while their modal is open were never tested. If back dismisses the modal without the SDK reporting it, the order is left PENDING with stock held and no signal.
Fix
Test it on a real Android phone before launch — beta task 3. If back escapes silently, add a popstate handler that treats it exactly like payment_aborted.
14

Payment failures

Needs workP0
Evidence
Success, abandonment and resume are all verified in the sandbox. A “Complete payment” retry exists on the order page and was driven to PAID. Totals are reconciled from payment_amount, not order_amount — a bug that once left an invoice overstating price and GST by 16% while 56 unit tests stayed green. A declined payment has never been reproduced: the sandbox's FAILED control refuses automated clicks.
Problem
The most common real failure — a declined card — is the one path nobody has watched. It is written defensively but unproven.
Fix
Drive it manually with UPI VPA testfailure@gocash, then testinsufficientfunds@gocash and testtimeoutbank@gocash. Confirm the order shows FAILED, retry works, and stock is not double-held. Thirty minutes of manual work.

Analytics

PassP2
Evidence
First-party only. Three events — page_view, product_view, whatsapp_order_click — checked against an allowlist server-side and ignored rather than rejected if unknown, so a stray event never surfaces an error mid-journey. Stored: event, product, variant, session, path, referrer (truncated to 500), device type, and user id only when signed in. No IP, no user agent, no third-party tracker anywhere.

17

Crash reporting

One value awayP1
Evidence
Sentry is wired into the storefront and the API, and does nothing without a DSN — verified the API boots and serves with SENTRY_DSN unset. Both error boundaries report with the digest attached as a tag, so the reference a customer reads off the error screen finds a real trace. sendDefaultPii is off and session replay is off, because this app handles phone numbers and delivery addresses and the defaults would put both in every report.
Problem
Still reporting nowhere until a DSN exists, so on launch day an error is currently invisible.
Fix
Two DSNs pasted into Render and Vercel. Steps in docs/switching-on-monitoring.md. No deploy needed — and the SDK is lazy-loaded, so an unconfigured reporter now costs no bandwidth either.

Accessibility

PassP1
Evidence
Lighthouse accessibility 100 on home, the shop listing and the policy pages. All 23 image tags carry alt text; heading order is nested correctly on all four page types. Seven real defects found and fixed: an ARIA role on an incompatible element, headings skipping h1→h3, an unlabelled sort control, step numerals at 2.27:1 against their own circle, five star-rating buttons with no accessible name, and review labels not associated with their inputs.
The one Lighthouse could not see
The sign-in dialog was unusable without a mouse. Tab walked straight out of it into the page behind — content hidden under the modal — twelve tabs never reached its own close button, and Escape did nothing. A keyboard-only customer could open it and had no way to shut it short of reloading. Fixed with a focus trap, focus restore, Escape, and proper dialog semantics; four cases in keyboard.spec.ts. A skip link now precedes eleven tab stops of navigation.
Problem
No screen reader has been used on this site. Automated checks do not press Tab and cannot judge how something is announced.
Fix
One VoiceOver pass, homepage to completed order, no mouse. Cashfree's own modal is outside your control — check it is reachable and escapable.

Serious issues outside the checklist

Three of these outrank most of the twenty.

Live credentials in git history, unrotated

P0
Evidence
apps/api/.env.disabled is tracked in git and contains a live DATABASE_URL and JWT_SECRET. Supabase connection strings were also pasted into a chat transcript in an earlier session.
Problem
Anyone with repository history holds the production database and can mint valid session tokens for any account.
Fix
Rotate both, then untrack the file. Untracking alone fixes nothing — the values are in history. This needs your dashboards; I cannot do it for you.

Stock from abandoned checkouts is released again

Resolved
Was
The sweep was written and tested and nothing called it — no @Cron, no ScheduleModule, nothing in render.yaml. Every abandoned checkout reserved jars indefinitely, showing as “out of stock” on a product with plenty on the shelf.
Now
POST /orders/cron/expire-abandoned behind a shared secret, called by a GitHub Action every fifteen minutes. The secret is compared in constant time, an unset secret closes the route rather than opening it, and the route accepts no body — so there is no olderThanMinutes to set to zero and turn a routine ping into a mass cancellation. Four tests, one named after the empty-matching-empty failure.
Evidence
The first real call released four orders that were holding stock at that moment. This was costing sales, not hypothetically.
Still needed
One generated secret in Render and GitHub. Until both exist the workflow exits without calling anything.

One Click Checkout is not activated in production

P0
Evidence
The Cashfree dashboard still shows “Request Activation” for production; only Test is live. Every payment result in this document is sandbox. The console also still reads testMerchantName with no logo uploaded.
Problem
There is no production payment path. Nothing can be sold.
Fix

Gateways generally check for live privacy, terms, refund and shipping policies, which is why those pages went up; they still need the seventeen business facts filled in, including the FSSAI licence number, which a food business selling online is legally required to display.

The mobile app is stale and unaccounted for

P1

Guests cannot reach their own order

P1
Evidence
The return page confirms with a claim token and works without a session, and the guest is auto-signed-in on confirm. But the order page itself requires a session — if (!user) setIsAuthOpen(true) — and there is no guest order-tracking route.
Problem
A guest who clears storage, switches device, or whose auto-sign-in fails cannot see the order they just paid for. With OTP delivery down in production, they cannot sign in to recover it either. These two failures compound.
Fix
Either a tokenised order-status link emailed on confirmation, or ship OTP so signing in actually works. The second fixes more.

Beta test plan

Five testers who have not seen the site, on their own phones, over one week. Recruit at least two who are not comfortable with online payments — they will find things the rest of you cannot see any more.

Five realistic tasks

  1. Buy a jar of ghee without making an account. Say nothing else. Watch whether they hesitate when a payment window they did not expect takes over the screen.
  2. Find out what is actually in the ghee, and whether it has been tested. Do not tell them about batch reports. This tests whether the purity claim is findable at all.
  3. Start buying the 500ml jar, then change your mind and buy the 1 litre instead. Exercises the basket-change path, which forces a new gateway order.
  4. Come back tomorrow and find the order you placed. The returning-customer path, and today the one most likely to fail.
  5. Order a jar to be delivered to a relative in another city. Tests whether the split between buyer and recipient is understandable, not just correct.

Five questions for testers

  1. At any point, were you unsure whether your money had actually gone through? Where exactly?
  2. When the payment window opened, did you know whose it was — and did that make you more or less willing to continue?
  3. What did you expect to happen after paying that did not happen?
  4. Was there anything you wanted to know before buying that you could not find?
  5. If this were your money and not a test, what would have stopped you?

What testers should record

  • Device, OS version and browser on every report — most of what will go wrong here is device-specific.
  • A screenshot or screen recording of anything unexpected, including the URL.
  • The order number and roughly what time, so it can be matched against the gateway and the logs.
  • Anywhere they waited and were not sure whether it was working — the gap between tapping and feedback.
  • Any wording they had to read twice, and any number that looked wrong.
  • Every point where they nearly gave up, even if they eventually got through. That one matters most and is the one testers routinely do not mention.

Prioritised plan

In order. The first group is not a backlog — nothing ships until it is done.

P0 — launch blockers

The sweep and crash reporting are built and have moved to P1, needing only a value pasted in. These three cannot be prepared from the repository at all.

  1. Rotate the leaked DATABASE_URL and JWT_SECRET, then untrack the file. Anyone with repository history holds the database and can mint session tokens. Untracking alone fixes nothing — the values are in history.
  2. Request production activation for One Click Checkout, and set the real merchant name and logo in place of testMerchantName. This is a review with a lead time, so it should start regardless of everything else.
  3. Reproduce a declined payment by hand. Success, abandonment and resume are all verified; the most common real failure is the one nobody has watched. The sandbox refuses automated clicks, so it needs a person and about thirty minutes — UPI VPA testfailure@gocash, then confirm the order reads FAILED, the retry works, and stock is not held twice.

P1 — before launch

Everything that could be done from the repository has been. What is left needs your accounts, your business decisions, or a real person.

  1. Paste two Sentry DSNs into Render and Vercel, and one generated secret into Render and GitHub. Both features are built and inert; these are the values that switch them on. docs/switching-on-monitoring.md.
  2. Make customer sign-in work in production. Phone OTP is the only method and the message channel throws without WhatsApp credentials, so a returning customer currently cannot get back into their account. Everything else about the account system is finished and unusable without it.
  3. Fill the seventeen business facts, FSSAI licence first — a food business selling online is legally required to display it — and have a lawyer read the four policy pages.
  4. Test back navigation during the payment modal on a real Android.
  5. One VoiceOver pass, and one real-device pass per the matrix.
  6. Run the beta. One week, five testers.

P2 — after launch

  1. Automated order notifications, once WhatsApp is live.
  2. Refunds. The schema is ready — REFUNDED, PARTIALLY_REFUNDED, Payment.refundedAmount — and nothing is wired to it. Deliberately left until the return window and postage rules are decided, since building the mechanism before the policy means guessing at both.
  3. COD, if it is offered at all — still an open question on the FAQ.
  4. Guest order tracking, if phone sign-in turns out not to cover it.
  5. Trim the storefront bundle further. It is 838 KB now, down from 1,014 KB; the rest is React, Next's runtime and component code, and going lower trades real complexity for diminishing returns.
  6. Apply the unsaved-changes hook to the other long admin editors if they start losing work.
